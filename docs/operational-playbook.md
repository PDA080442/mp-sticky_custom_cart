# Эксплуатационный playbook (MP Sticky Custom Cart)

Документ закрывает задачи фазы **11.4** плана разработки: процедуры включения флагов, разбор ошибок, проверки после обновлений Woo/темы, чтение логов не-разработчиком, health-check перед релизом, fallback при сбоях и SLA инцидентов.

---

## 1. Включение фич по feature flags — Document Feature Flag Rollout Steps

**Где настраивается:** WordPress Admin → **Sticky Cart** → вкладка **Служебное** (или аналогичная), блок **Feature flags**.

**Рекомендуемый порядок**

1. **Стейджинг или копия продакшена** — сначала включить флаг на среде, максимально близкой к бою (те же Woo, тема, кэш).
2. **Один флаг за раз** — если поведение связано (например sticky + drawer), фиксируйте комбинацию в чек-листе и включайте пакетом только после отдельной проверки каждого.
3. **Дымовый сценарий (5–10 мин)** после каждого изменения:
   - каталог: клик по изображению / overlay (если включено);
   - sticky: открытие drawer, +/- количества, удаление строки;
   - checkout: переход с sticky без ошибок.
4. **Наблюдение 24–72 ч** — вкладка **Диагностика**: журнал ошибок, клиентское логирование (если включено). Резкий рост `error` / `xhr_ajax_error` — повод откатить флаг.
5. **Откат** — снять галочку с флага, сохранить настройки, очистить кэш страницы/оптимизатора при необходимости. Зафиксировать время и версию плагина в тикете.
6. **Документирование** — кто согласовал включение на проде, дата, список проверенных URL.

**Не включать на проде** одновременно с крупным обновлением Woo/темы без отдельного окна проверки.

## 2. Диагностика частых ошибок — Document Common Error Triage

| Симптом | С чего начать | Типовое действие |
|--------|----------------|------------------|
| Sticky не обновляется после добавления в корзину | Сеть: запросы к `admin-ajax.php`, ответы 200/403/500 | Проверить nonce/сессию, конфликт плагинов безопасности, отключить кэш для `admin-ajax.php` по правилам хостинга |
| Повторяющиеся `xhr_ajax_error` / `fetch_http` в журнале | Фильтр по endpoint / периоду | Сверить версию Woo; временно отключить минификацию/объединение JS |
| `js_error` / `unhandledrejection` на конкретной странице | URL страницы в записи, user-agent | Воспроизвести в инкогнито; искать конфликт темы/плагина на этой странице |
| `woo_cart_snapshot_sync_fail_burst` | Нагрузка / таймауты сервера | Логи сервера (PHP-FPM), лимиты времени выполнения; не дублировать отчёты без новых данных |
| Записи уровня `info` | Ожидаемые клиентские события | Не трактовать как поломку без контекста бизнес-логики |

**Порядок эскалации:** L1 (настройки + логи плагина) → L2 (логи сервера, конфликт плагинов) → L3 (разработка, воспроизведение на копии).

## 3. Проверка после обновления WooCommerce — Document PostWooUpdate Validation

Выполнить **в течение первого рабочего дня** после обновления WC (и при мажорных — в первые часы).

**Обязательный минимум**

- [ ] Статус Woo: нет критических уведомлений в **WooCommerce → Статус**.
- [ ] Каталог: добавление в корзину с листинга и со страницы товара (в т.ч. вариативный, если используется).
- [ ] Sticky: снимок корзины, изменение количества, удаление позиции, кнопка «Оформить заказ».
- [ ] Checkout: оформление тестового заказа (или до оплаты — по политике магазина).
- [ ] Фрагменты корзины / мини-корзина темы: нет дублирования счётчиков и конфликтующих notice.
- [ ] **Диагностика** плагина: нет всплеска ошибок с тем же временем, что и обновление.

При регрессии — зафиксировать версии **Woo + тема + плагин**, откат WC по процедуре хостинга или точечный hotfix.

## 4. Проверка после обновления темы — Document PostThemeUpdate Validation

Тема влияет на вёрстку, z-index, хедер и mobile.

**Чек-лист**

- [ ] Sticky-панель видна там, где должна (главная, каталог, карточка товара, по политике проекта).
- [ ] Drawer не перекрыт фиксированным хедером/кнопками темы; при необходимости подстроить CSS-переменные плагина (**Стили**).
- [ ] Каталог: клик по изображению / overlay не уводит на неверный URL и не ломает add-to-cart.
- [ ] Mobile: ширина viewport, отсутствие горизонтального скролла из-за sticky.
- [ ] Кэш страницы/OPcache сброшен после выкладки темы.

При child theme — проверить, что переопределения шаблонов Woo не устарели.

## 5. Чтение логов для менеджера — Document NonTechnical Log Reading Guide

**Где смотреть:** **Sticky Cart → Служебное → Диагностика → Журнал ошибок** (доступ ограничен правом управления диагностикой плагина).

**Что означают колонки**

- **Время (UTC)** — время сервера в UTC; для локального времени магазина ориентируйтесь на настройки сайта или конвертируйте вручную.
- **Уровень** — `error` / `warn` приоритетнее для эскалации; `info` и `debug` часто диагностические.
- **Источник / endpoint** — откуда пришла запись (клиентский батч, AJAX и т.д.).
- **Сообщение** — краткий текст; полные детали — по клику на строку (drawer) или экспорт.

**Как действовать**

1. Отфильтровать по **дате** инцидента и по **уровню** `error` / `warn`.
2. Нажать на строку и при необходимости сохранить JSON для разработчика.
3. **Экспорт CSV/JSON** — для приложения к тикету; не публиковать публично (там могут быть URL, user-agent, хеш IP).
4. Если записей нет при жалобе пользователя — проверить, включено ли **логирование JS/AJAX** в настройках диагностики.

## 6. Минимальный health-check перед релизом — Document PreRelease Health Checklist

Перед выкладкой новой версии плагина на прод:

- [ ] Версия в заголовке плагина и константах согласованы.
- [ ] Пройдены автоматические/ручные тесты проекта (`tests/*.test.js` при наличии CI).
- [ ] На стейджинге: сохранение настроек, smoke по каталогу + sticky + checkout.
- [ ] Feature flags: на проде по умолчанию **безопасная** конфигурация (что согласовано с владельцем).
- [ ] Резервная копия БД/файлов по регламенту хостинга перед деплоем.
- [ ] Changelog / заметки к релизу для команды поддержки.

## 7. Fallback при сбоях endpoint — Document Runtime Fallback Actions

**Если не отвечает `admin-ajax.php` или падают запросы плагина**

1. Пользователь: обновить страницу; при повторении — другой браузер/сеть.
2. Оператор: проверить статус хостинга, лимиты rate-limit/WAF для `admin-ajax.php`.
3. Временно отключить агрессивный кэш для залогиненных или исключить URI AJAX из full-page cache.

**Если отваливается только снимок корзины (sticky «завис»)**

- Триггернуть обновление корзины Woo (переход на страницу корзины / событие темы).
- Включить в тикет: время, URL, экспорт строк журнала с `cartSnapshot` / snapshot sync.

**Если нужно срочно стабилизировать витрину**

- Отключить отдельные **feature flags** (например клик по изображению), не отключая весь Woo.
- Не снимать плагин с прода без бэкапа и плана отката.

## 8. SLA реакции на критические ошибки — Document Incident Response SLA

Критическая ошибка: **невозможность оформить заказ**, **массовая недоступность корзины**, **утечка данных** (последняя — по отдельному регламенту безопасности).

| Приоритет | Примеры | Цель первой реакции | Цель временного обхода / фикса |
|-----------|---------|---------------------|--------------------------------|
| P1 критический | Checkout недоступен многим пользователям | ≤ 1 ч (рабочее время команды) | ≤ 4 ч |
| P2 высокий | Sticky сломан, но классическая корзина Woo работает | ≤ 4 ч | ≤ 1 рабочий день |
| P3 средний | Редкий JS в логах, обходной путь есть | ≤ 1 рабочий день | по плану спринта |

**Вне рабочего времени:** P1 — по договорённости с владельцем проекта (duty phone, мониторинг хостинга).

**После инцидента:** короткий postmortem (что сломалось, что сработало, что улучшить в мониторинге и флагах).
